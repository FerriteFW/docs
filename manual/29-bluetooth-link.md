## 29. Bluetooth, the cable and the web app

### What it's for

One open link protocol connects the radio to Ferrite's own web app, over the programming cable or Bluetooth: codeplug, logs, live events, waypoints, backups, the remote head and firmware install.

### Using it

**Cable:** the programming cable on the side connector (UART4). Open the web app; it connects over Web Serial at 115200, then moves to a faster rate.

**Bluetooth:** MENU 0 9 2 1 on (off by default); turning it on is your consent to connect. The phone pairs with the module itself; MENU 0 9 2 2 shows the link. The status bar shows the Bluetooth icon while a device is connected (the radio can only tell from the device sending something: LINK-29). Bluetooth carries the same link protocol and terminal as the cable, or KISS (0 5 8), at the module's 9600 baud, sent in bursts the module can forward (about 0.3 KB/s from the radio, LINK-36). A link session can run on the cable and on Bluetooth at the same time; writes go one port at a time. The terminal runs on one port at a time, and the cable always takes it back (LINK-28).

**From a computer:** `ferrite/tools/webble/index.html` is a Web Bluetooth page for Chrome (served from localhost: `python3 -m http.server` in that folder): the screen read back, the keypad and knob, the command line and, with Dry TX on only, remote PTT behind an Arm switch. `tools/ferrite_link.py ble:walkie-talkie ...` does the same from Python (bleak).

**iPhone:** Safari has no Web Bluetooth or Web Serial. Use **Bluefy**; the web app says so when it finds no Bluetooth.

**The radio's PIN on Bluetooth:** while a PIN lock is on (MENU 0 9 3 1), every Bluetooth connection asks for the radio's own PIN before anything else: the terminal shows `PIN:`, and the web app asks you to type it. Wrong PINs count with the radio's own (three, then a 30 s wait, shown on the radio too). With no PIN lock, a Bluetooth connection reads and writes like the cable. The cable never asks: it needs the radio in your hands.

**KISS mode** (MENU 0 5 8) turns its port into a raw KISS TNC; the link protocol is off on that port while it's on (chapter 26).

**During a write session** the radio shows progress (item, %); keys are ignored except **BACK**, which cancels.

**Remote head:** the web app shows the radio's screen and sends keys from the PC keyboard.

The web app does: channels, zones and settings; CHIRP CSV and RepeaterBook import; event log and APRS messages; waypoints; the full-flash backup; stock backup and restore; firmware flashing (chapter 30); SSB patch import; live events and the PC audio stream (cable only).

> **Spec: protocol**
>
> - **LINK-1** One protocol on cable and Bluetooth: COBS frames with type, sequence number, payload and CRC-16; every frame acknowledged.
> - **LINK-2** Messages (Appendix G): `HELLO`/`INFO`, `AUTH`, `READ`/`WRITE` (records bigger than a frame), `DELETE`, `BEGIN`/`END`, `USED`, `READ_MANY`/`WRITE_MANY` (channels, zones, presets and their skip lists, contacts, channel positions, quick messages, waypoints, DTMF memories), `STREAM`, `LOG_READ`, `SLOT`, `CMD`/`MORE`, `KEY`, `UI`, `SUBSCRIBE`/`EVENT`, `HEARD`, `MSGS`, `MSG_SEND`, `MSG_STOP`, `MSG_DELETE`, `AUDIO` (with `AUDIO_DATA` and `AUDIO_RAW`), `BAUD`, `REBOOT`, `STOCK_RESTORE`, `DATA_READ`/`DATA_WRITE` (the SPI flash's data range raw, for Console's update: LINK-59 – LINK-62), `CLOCK` (LINK-65), satellites and their info by `READ_MANY`/`WRITE_MANY` (LINK-63, LINK-64), and compression's wrapper (LINK-51). The whole chip's backup at install is the installers' and the backup reader image's (BACKUP-9); KISS runs on a port of its own (KISS-6); the screen mirror is shelved (LINK-18). Protocol 3 (decision 333): zone numbers are 2 bytes, a zone record ends with its channel count, `USED` goes in parts, and `HELLO`/`INFO` end with the layouts.
> - **LINK-3** As SAFE-5: no `CAL_WRITE`; no message touches calibration or the update area.
> - **LINK-4** As SAFE-5: `STOCK_RESTORE` skips calibration and the update area.
> - **LINK-5** Writes are validated: frequencies, tones and power must be legal for the band; TX limits and region can't be changed over the link.
> - **LINK-6** The protocol definitions are shared with the web app and versioned with the firmware; the spec is published (Appendix G).
> - **LINK-21** Version 1 reads and writes four records: settings, channels, zones and range presets, in the radio's own byte layouts (Appendix G). `READ` and `WRITE`, which go in parts, are for the records bigger than a frame only: the settings and the APRS record (LINK-43). Channels, zones and presets go whole, several to a frame, by `READ_MANY` and `WRITE_MANY` (LINK-40, LINK-41); a `READ` of one answers `bad argument` and a `WRITE` `refused` (LINK-3), changing nothing. Records are never addressed by flash location; the raw data messages (LINK-59, LINK-60) are apart from them, for moving data between layouts, and never reach calibration or the update area. A settings read gives the PIN as zeros; a settings write keeps the radio's region, Extend TX, PIN, setup state, cable port and KISS port, whatever the record says, and writes the callsign (LINK-26).
> - **LINK-22** Channels written over the link get the same checks as the radio's editors and the terminal's `ch` (frequency range, split and the relay: LINK-5, TX-37); a refusal answers `invalid` with the reason as text. A channel or setting open in the radio's own editor isn't changed (the radio wins, as TERM-17); the link answers `busy` and the PC tries again.
> - **LINK-24** `REBOOT` restarts the radio into the stock bootloader for a firmware update.
>     - **LINK-24.1** `REBOOT` from the cable: the answer goes out first; then the radio goes quiet (Shutdown), writes what is pending (at most 3 s) and does a system reset, as hwtest's `reboot` does, so the stock bootloader listens for the updater. `flash.py` sends it before probing.
>     - **LINK-24.2** From Bluetooth too, past the PIN while a PIN lock is on (LINK-30).
>     - **LINK-24.3** Refused `busy` while transmitting, a data key-up (APRS, KISS) included (decision 175).
>     - **LINK-24.4** Option bytes are never touched.
> - **LINK-25** Bluetooth: USART1 runs at 9600 8N1, the rate the BT513 rests at (decision 152). Stock sends its KISS(BLE) frames to the module at 9600 (V0.27 0x08016EEC switches USART1 to 9600 for the frame, then back to 115200); stock's own 115200 is for its CPS programming, most likely after the vendor's app has set the module's rate over FF31. At 115200 nothing got through on the bench (Oct 14, 2026). The radio sends a Bluetooth byte only when USART1 takes it without waiting (about 1 ms each), so the shared task never stalls, and in paced bursts (LINK-36). The radio's Bluetooth item is on/off (PB9), as stock: the MCU never configures the module, so pairing, the name and its rate are the module's; after each transmission PB9 is re-asserted when Bluetooth is on, as stock.
>     - **LINK-25.1** USART1 goes back to 9600 whenever the radio powers the module (boot, Bluetooth on): a module powered off and on has lost an unlocked rate (bench, Oct 24, 2026). A key-up doesn't touch it (the module stays powered; checked on black: 115200 held across a key-up).
>     - **LINK-25.2** A framing error on USART1 moves it to the other of 9600 and 115200, at most once in 300 ms and not in the first 300 ms after the module is powered: the module talks the other rate (an unlock that didn't take, a radio restarted while the module kept its rate).
> - **LINK-28** The cable and Bluetooth each run their own link session, at the same time (decision 152): each port's frames, `HELLO`, PIN, running `CMD` and write session are its own, and each answer goes back on the port it came from. What the two share is kept safe:
>   - Writes go one port at a time: a `WRITE`, `WRITE_MANY`, `DELETE` or `BEGIN` from one port while the other is mid-write (a write session between `BEGIN` and `END`, or a record half sent) answers `busy`; reads go on.
>   - Remote PTT has one keyer (LINK-20): the port that keyed. The other port's key-up and keepalives answer `invalid` ("keyed from the other port") and don't hold the transmission; its `KEY` off still unkeys (stopping is always allowed). Keepalives are per session: the keyer's must keep coming. A session starting over ends only its own transmission and the remote keys it holds; remote keys held from one port make the other's `busy` until let go.
>   - The firmware's debug requests (`CMD`'s `bk`, `mem`, `bt` ...) go one at a time; another waits for the answer (at most 2.5 s).
>   - The VT100 terminal stays single, held by one port at a time: the cable always takes it (physical access, LINK-7; also the way back from a phone that left it open), Bluetooth when the cable's terminal is closed; meanwhile Bluetooth's terminal bytes are dropped. A link session never takes or blocks the terminal. (One terminal: a second screen state costs RAM, and `CMD` runs the same commands on either port.)
>   - KISS needs neither, so it runs on its port beside the other (KISS-6).
>   - On Bluetooth the terminal and the link each ask for the radio's PIN while a PIN lock is on (LINK-30); the PIN given lasts for that connection.
>   - `BAUD` never applies to Bluetooth (LINK-15). (Decision 90, Oct 8, 2026, held one terminal and one session for both ports; decision 152 gives each port its session, about 0.8 KB of RAM.)
> - **LINK-29** A Bluetooth connection is taken as over when the device has sent nothing for 2 minutes, or when Bluetooth is turned off (0 9 2 1): the module tells the radio nothing about connects, as it is a transparent bridge (LINK-25). Its terminal closes and the PIN it gave ends with it; the status bar's Bluetooth icon shows a connection by the same rule.
> - **LINK-30** While a PIN lock is on (0 9 3 1 not Off, with a PIN set: PIN-1), every Bluetooth connection gives the radio's PIN before anything else: the terminal shows a `PIN:` prompt (digits shown as *) and reads nothing else until it's right; the link protocol answers `HELLO` (its third byte 0: `AUTH` first) and `AUTH`, and every other request `not authorised`, until an `AUTH` carrying the PIN passes. It is the radio's own PIN (0 9 3 3), no separate one. The PIN given lasts for that connection (LINK-29); the next asks again. With no PIN lock nothing is asked.
> - **LINK-31** Wrong Bluetooth PINs count with the radio's own (PIN-3): the third wrong one starts the 30 s wait for the keypad and every Bluetooth attempt (`AUTH` answers `busy`; the terminal says how long), and each wrong one shows on the radio's screen as a toast ("Wrong PIN, Bluetooth"; "PIN locked 30 s"). The cable is never asked (physical access, LINK-7).
> - **LINK-32** Retired (decision 104): a Bluetooth write needed both the PIN and an approval token; tokens and the on-screen approval are gone, so the PIN (LINK-30) is the only Bluetooth check.
> - **LINK-26** A settings write sets the callsign, in capitals as typed on the radio (SETUP-12); the session's access (LINK-7, LINK-30) is enough, as nicFW's RMS writes it. Region, Extend TX, the PIN, setup, the cable port and the KISS port (KISS-7) keep the radio's values (LINK-5); Low Power Mode and its Auto level are written (PWR-24.1, decision 328).
> - **LINK-39** `USED` says which channel numbers hold a channel, one bit each (zones and presets too, all held from 0 up): a PC reads only those. Protocol 3 (decision 333): from a first index, as many as fit an answer (1,880), so 4,000 channels take three asks; the answer says the index count and the first index it maps.
> - **LINK-40** `READ_MANY` reads whole channels, zones or presets from a first index on, as many as fit in one answer (240 bytes: five channels), skipping empty numbers, and says where to go on from. It is the only way to read them (`READ` is for the settings and APRS records, LINK-21).
> - **LINK-41** `WRITE_MANY` writes several whole channels, zones or presets in one frame, applied in order, each with exactly the radio's editors' checks and the busy rule (LINK-5, LINK-22); it is the only way to write them (LINK-21) and counted on the progress screen (LINK-9); a refusal stops it there, and the answer says how many went before it. A malformed frame changes nothing.
>     - **LINK-41.1** A `WRITE_MANY` of channels goes to the store's own queue (8 writes, decision 287) record after record in one pass, without waiting for each to be written, so channel writes to the same flash sector are merged into one rewrite (decision 227); it waits only while the queue is full or holds anything but channel writes (a zone being created is stored before a channel that names it is checked). Zones and presets go one at a time, each after the store is idle, as before. Each UART's receive ring holds 512 bytes, room for a whole second frame, so a client may keep two `WRITE_MANY` frames in flight (LINK-35.2); answers come in order.
>     - **LINK-41.2** A `WRITE_MANY` channel record of length 0 deletes that channel, as `DELETE` does (slots on it go to VFO, the home channel cleared), through the store's queue so deletes in one sector share its rewrite (decision 286): 1,000 channels in 14-15 s instead of 189 s one `DELETE` each. None there: nothing to do. Old radios answer `bad argument`; Console and `ferrite_link.py` use it when `HELLO` says so (LINK-35.2).
> - **LINK-42** `LOG_READ` reads the event log (INBOX-6) newest first, in parts: from below a sequence number, as many records as fit, each with its sequence number, its age in seconds, source, slot, read mark, frequency, ID, position, name and text (Appendix G). Sequence numbers only grow, so a PC goes on from the last it got while new events arrive. Reading marks nothing read.
> - **LINK-43** The APRS settings (MENU 0 5's frequency, beacon mode, power, path, digipeater, beacon after voice, SSID, custom path and FX.25 on transmit: the APRS record's, not in the settings record) read and write over the link as one record, `what` 5 (Appendix G). A written record is checked as the radio's editors check each value (0 5 4's 64–300 MHz on its 5 kHz grid, the region's own frequency kept as the region's; 0 5 9 2's path, APRS-26; the SSID 0–15, APRS-30; the beacon modes, power and digipeater wait 0 5 6 1, 0 5 6 3, 0 5 7 3 offer); any value refused answers `invalid` with the reason and changes nothing. As with the settings, it is written whole: Console reads it first and keeps that as the backup it can write back. The quick messages aren't in it. Since decision 347 (radios that say caps2 `RADIO`) the record also holds the message sound (0 7 5 5), symbol, TX delay, TX level, comment (printable ASCII, 40 at most), ambiguity, Mic-E and telemetry, each checked as its editor checks it, so Console needs no line commands for MENU 0 5; a shorter record keeps the radio's values past its end.
> - **LINK-44** `HEARD` reads the heard list (APRS-3, APRS-4: callsign, symbol, age, times heard, the last position, course and speed, altitude, the path it came by, the comment) and `MSGS` the messages in and out, newest first (who, the text, age, state and tries: APRS-13), each from any index, as many whole records as fit an answer. Reading marks nothing read.
> - **LINK-45** `MSG_SEND` queues an APRS message exactly as compose's Send does: APRS-8's callsign, the store's queue, APRS-13's tries, the toast "Message queued"; the radio's own draft is left as it was. Its transmissions follow every rule a message's do (APRS-7, APRS-10, APRS-20, chapter 15; Dry TX as set, TX-48): it goes while APRS mode is on, else waits for it (APRS-22), and the answer says which. Refused, `invalid` with the reason: a receive-only build, no callsign, an address that isn't 1–9 capitals, digits and `-` (lower case is taken as capitals), or a text that isn't 1–67 printable characters without `|`, `~` or `{`. It is the session's own request, as remote PTT is (LINK-20); remote keys still never send one (LINK-19).
> - **LINK-46** `SUBSCRIBE` asks for events: a mask of stations heard, messages, Live View (LINK-47) and the event log (LINK-57). One subscription per session, replaced by the next `SUBSCRIBE`; it ends with the session (a new `HELLO`, a new connection: LINK-29), with a mask of 0, or after 10 s with no frame from the session (`SUBSCRIBE` with the renew flag keeps it, changing nothing). `EVENT` frames then come unasked, each with its own counter: only while no request waits for its answer and the port keeps room for an answer after it, and within 200 bytes a second on Bluetooth (of LINK-36's ~280, leaving the rest for answers; the cable 4000), up to 300 saved. Only what happens after the subscription: the newest station heard, with the list's count; a new message, in or out; a message's state changed (acked, retrying, failed, read); and Live View's updates.
> - **LINK-47** Live View is the UI readback (LINK-19) made small for Bluetooth: its lines, up to 48, less `state`'s `frame=` and `ago=` (they move on every redraw), each line cut after its last whole token that fits 230 coded bytes, coded with a 31-entry text dictionary (Appendix G). The text readback (`UI`, `ui`) stays as it is. One Live View at a time, the newest subscription's; the other port's stops.
> - **LINK-48** Live View sends the whole compact state once (over more than one event when it doesn't fit one), then only the lines that changed since the last update the session was sent: a whole line, or the tokens that changed (a value alone when its key is the one there). Each update is numbered; a client that misses one, or whose lines don't add up to the update's check (16 bits of FNV-1a over the lines), asks for the whole state again (`SUBSCRIBE` without renew). Updates go when something was redrawn, at most every 500 ms on Bluetooth (200 ms on the cable; `SUBSCRIBE` can ask another gap, in 100 ms steps), and 100 ms after a key or the knob (for what changes within a second of one too). Measured on the simulator over Bluetooth (Oct 20, 2026): an idle home screen, the meters and the clock moving, about 36 B/s (an update about every second, 20–40 bytes); a scan 20–70 B/s; opening a menu about 330 bytes, a little over a second at Bluetooth's pace.
> - **LINK-49** `MSG_STOP` (0x55) stops one of your messages still being tried, as the radio's Stop sending does (APRS-13.1): its payload is `MSG_SEND`'s (the station, then the text); the newest of yours to that station with that text still being tried ends as cancelled. Answered `invalid` ("not being sent") when there is none; firmware from before it answers `unknown type`. `MSGS` gives a cancelled message state 7 (LINK-44). Decision 284.
> - **LINK-50** `STREAM` (0x19) asks one request's answers back to back (decision 285): its payload is `READ_MANY`'s, `HEARD`'s, `MSGS`'s, `LOG_READ`'s or `UI`'s type and payload (anything else answers `bad argument`). The radio sends that request's answers in turn, each as asking again from where the last left off would give, framed `STREAM_MORE` (0x1A) while more follow and `STREAM` for the last; the first carries the request's seq and each next one seq + 1, so a frame lost on the way shows as a gap and the client asks again from the last it has. Frames go as the port has room (flow control by the link itself); any new request ends a stream. Only from radios that say so in `HELLO` (LINK-35.2).
> - **LINK-51** Compression (decision 286): a `HELLO` whose first reserved byte has bit 0 set asks for it, and gets it (capability 4) when the radio's one compression block is free: first come, first served; the other port's session runs plain meanwhile, and the block is free again when its session ends (a new connection, a `HELLO` not asking, 10 s quiet). From that `HELLO`'s answer (always plain) both ends start new windows: LZSS (`ferrite_core::linkz`, `tools/linkz.py`) over what each direction carried, 1 KB radio to PC and 512 bytes PC to radio, 512 hash heads with the newest position each. A frame whose payload codes shorter goes as type 0x7D (0xFD for an answer) with the inner type, the frame's count in its direction and the coded bytes; else plain; every frame, plain or coded, goes into its direction's window and count. A coded frame whose count doesn't match (a frame lost on the way) is dropped; the client, hearing nothing, sends a `HELLO`, which starts both ends over, and asks again. The radio's side: 2.5 KB of windows and heads and 0.5 KB of frame buffers, one block for both ports; about 240 cycles a byte to code (3 ms for 1.5 KB at 120 MHz), 120-240 to decode.
> - **LINK-52** `MSG_DELETE` (0x59) deletes one APRS message, as the radio's Delete message does (APRS-46.1): its payload is a flags byte (bit 0: a message to you; clear: one of yours), then `MSG_STOP`'s station and text; the newest message that way with that station (any case) and that text goes. Answered `invalid` ("no such message") when there is none; firmware from before it answers `unknown type`. Decision 323.
> - **LINK-53** Channel positions (decision 325): `READ_MANY` and `WRITE_MANY` of `what` 7 read and write a channel's position by its number, latitude and longitude in 1e-7 degree (Appendix G), the ones the channel record holds (CHAN-2), so Ferrite Console can show and set them. A read lists only the channels that have one, from the store's zone map and each record, as a channel read does. A write is checked as the terminal's `pos=` is (latitude within ±90, longitude within ±180; `invalid` with the reason), a record of length 0 clears it, and a number with no channel changes nothing. It changes only the position: the channel's other fields stay as they are when the write is made, so a position sent right behind its channel's own write lands on that channel. Positions go to the store's queue as channel writes do (LINK-41.1) and share their sector's rewrite (decision 227): no erase beyond what writing those channels costs, and none for a position as stored. `HELLO`'s caps say 64 (LINK-35.2); an older radio answers `bad argument`, and an older Console never asks.
> - **LINK-54** Quick messages (decision 327): `READ_MANY` and `WRITE_MANY` of `what` 8 read and write the nine quick messages (TEXT-7) by number, 0–8: a flags byte (bit 0: the owner's own text; clear: the factory text), then the text the radio uses (Appendix G). A read lists all nine. A write with bit 0 set takes the text, checked as compose checks a message (up to 67 printable characters, no `|`, `~` or `{`; empty stays empty, as on the radio) or answers `invalid` with the reason; with bit 0 clear it puts the factory text back. A message as the radio has it writes nothing; a changed one saves the APRS record as the radio's own editor does (one erase of one of its two copies).
> - **LINK-55** Waypoints (decision 327): `READ_MANY` and `WRITE_MANY` of `what` 9 read and write the waypoints (GPS-10) by their place in the list, newest first (0 the newest): name (16 bytes), latitude and longitude (1e-7 degree), source (marked, APRS, link, grid) (Appendix G). A write at an index in the list replaces that waypoint in its place; at index 0xFFFF it adds one as the newest (`invalid` "2032 waypoints" when the store is full); a record of length 0 deletes the one at that index, as the radio's Delete does. Checked as a channel's name and position are (1–16 printable characters; latitude within ±90, longitude within ±180; a source 0–3), else `invalid` with the reason; another index `not found`. Each record waits for the one before it to be stored, so an index means the list as the records before it in the frame left it: a client deletes from the highest index down, then replaces, then adds. A waypoint as stored writes nothing; one added is programmed only; one replaced or deleted rewrites its sector once, through the scratch sector (a delete moves the later ones down, as GPS-10's).
> - **LINK-56** DTMF memories (decision 327): `READ_MANY` and `WRITE_MANY` of `what` 10 read and write the 16 DTMF memories and their names (DTMF-12) by number, 0–15: the symbols (a length, then 1–16 of `0-9`, `A-D`, `*`, `#` as text; lower case taken as capitals), then the name (up to 10 printable characters) (Appendix G). A read lists only the memories set. A record of length 0 clears the memory and its name; symbols or a name the radio's editor wouldn't take answer `invalid` with the reason. The symbols and the name are written each only when it changed: on a blank record, programmed only; over a stored one, one rewrite of their sector.
> - **LINK-57** The event log live (decision 327): `SUBSCRIBE`'s mask 8 sends each event logged after the subscription (INBOX-6, INBOX-11), oldest first, as `EVENT` kind 5 with the record as `LOG_READ` gives it (its sequence number first), within LINK-46's pacing (200 bytes a second on Bluetooth, about two events; the cable 4000), one a turn while no request waits; the ones the log has already dropped are skipped, and the client reads any gap with `LOG_READ`. A log cleared on the radio says nothing. It costs 4 bytes of RAM a session (the next sequence number to send).
> - **LINK-58** Range preset skip lists (decision 329): `READ_MANY` and `WRITE_MANY` of `what` 11 read and write a range preset's skipped frequencies (SCAN-10) by the preset's index (as `what` 4): up to 48, 10 Hz each (Appendix G). A read lists the presets that have any. A write replaces the whole list (a record of length 0 clears it); each frequency must lie within the preset's start and end and appear once, else `invalid` with the reason. The list is kept in the preset's own record, so it stays with its preset: deleting a preset before it changes its index, never its list, and a deleted preset's list goes with it; a preset rewritten at an index (`what` 4) keeps the list held there, so a client writes the lists after the presets. A list as stored writes nothing; a changed one goes to the store in four parts at most, each one rewrite of the presets' sector. Only from radios whose second capability byte says 1 (LINK-35.2).
>     - **LINK-58.1** A list read leaves out blank entries (erased flash's 0xFFFFFFFF, or 0: never a frequency), so a record holds only real frequencies; a preset whose entries are all blank isn't listed (decision 332).
> - **LINK-59** `DATA_READ` (0x61, decision 333) reads the SPI flash raw: up to 232 bytes from an address, or the CRC-32 of a range (Appendix G). It reaches the whole data range below the update area but calibration: a range touching 0x00F000–0x00FFFF or 0x300000 up is refused (`refused`, LINK-3), whatever the port. It answers `busy` while the store still has writes to make, the one the Storage task is doing included (decision 339: a read-back then holds them all, never half a write). Both ports, past `AUTH` where a PIN lock asks for it (LINK-30). It works whatever the chip holds, in particular while another layout's data waits for Console (UPD-16).
> - **LINK-60** `DATA_WRITE` (0x62) writes the data range raw: a 4 KB sector erased, up to 64 bytes programmed inside one 256-byte page (into erased bytes: a program only clears bits), or the layout header stamped (LINK-62). The same ranges as `DATA_READ`, held inside the flash driver's writable ranges too (SAFE-5): calibration and the update area are refused by construction (`refused`); a misaligned erase or a program across a page `bad argument`. The layout header and the migration mark (0x000000 and 0x00E000, Appendix G) are the store's own: a raw write there is `refused` (decision 339). The cable only (`refused` from Bluetooth, as `STOCK_RESTORE`); `busy` while the other port writes (LINK-28) or the store's queue is full (send it again). Each write goes to the store's queue and is done by the Storage task in order with the store's own; the answer comes when it is queued (decision 339: so the queue keeps the flash busy while frames cross the cable; nothing depends on an answer meaning "written", since each region is read back by CRC, which waits for the queue, the stamp waits for it too, and any restart waits for the store). Before the first raw write of a power-on the store puts down the migration mark, then this layout's header at 0x000000 (unless a good one is there), each read back (decision 339); the raw writes run only once that is done.
> - **LINK-61** The first raw write stops the store's own (decision 333): from then until the radio restarts it reads and writes no records (it would write over what Console writes, or read half of it), saves nothing, and shows D25 as for another layout's data (UPD-16); `HELLO` and `INFO` say the chip's layout as 255, half moved (decision 339). A restart after the stamp mounts what was written; a restart before it (`REBOOT`, a power cut) finds the migration mark and waits for Console (UPD-16).
> - **LINK-62** `HELLO` and `INFO` end with two bytes: the layout this firmware stores (3) and the one the chip's data is in (3 when all is well; 2 for layout 2's data, or another Ferrite layout's version: Console finishes the update; 255 while the data is half moved, LINK-61, UPD-16, which only Console's copy can finish, never the chip read back). The stamp (`DATA_WRITE` op 2 with layout 3) is taken only once the store has nothing queued or being written (`busy` before: send it again); it checks the layout 3 header the begin wrote and clears the migration mark, programming it to zero, each read back: no erase (decision 339). Then the radio restarts on it, as after `REBOOT`; the restart waits for the store to finish (up to 15 s after raw writes), and Console checks `HELLO` says 3 and 3 after it. Console moves data between layouts in this order, so an interruption at any point loses nothing: (1) `HELLO`: the layouts say what to do; (2) back up: `DATA_READ` the old layout's regions (for layout 2: 0x02C000–0x08CFFF, and its scratch ring 0x1E0000–0x1FFFFF, whose pending rewrite Console finishes in its copy) and keep the copy on the PC, checked by `DATA_READ`'s CRC, before anything is written (a firmware with `DATA_READ` before the update is read before flashing; layout 2's firmware has none, so its data is read once the new firmware waits with it untouched); (3) translate on the PC (Appendix G, "Layout 2 to 3"); (4) for each region of the new layout, erase its sectors and program its bytes, checking each region by CRC; the sector that holds the old header (layout 2: 0x02C000, in layout 3's channel sector 28) last of all, so until then a restart finds the old layout and stays waiting; (5) stamp the header last. A power cut or a reset at any point of (4) or (5) leaves a chip that boots waiting for Console (layout 2's header, or the migration mark: D25, layouts 3 and 2 or 255), never a format, or after the stamp the new layout with everything (decision 339). Started again after an interruption, Console begins at (3) from its copy (on another computer: the backup file, "Use a saved backup…").
> - **LINK-63** Satellites (SAT-2, decision 340): `READ_MANY` and `WRITE_MANY` of `what` 12, a satellite by its place (0-31), the record of Appendix G (status, flags, catalogue number, name, elements, up to five transponders with their tones and arming tones). A record replaces the satellite in its place; the satellite's own choices (trim, duplex, transponder, uplink power) are kept by its catalogue number, so a list written again keeps them; length 0 deletes it; length 0 at 0xFFFF deletes all of them in one rewrite, after which the list's records only program erased bytes. Each record is checked as SAT-2 and SAT-13 say: a transponder outside 144-148 or 430-440 MHz is refused (`invalid` and why), so the band relay never moves in satellite mode. A record the radio already holds writes nothing. One record waits for the store at a time (`busy`: send it again).
> - **LINK-64** The satellites' info, `what` 13, index 0: the declination at the radio (SAT-18), the satellite data's build time and when Console wrote it (SAT-21's "newer than what the radio holds" and "at most one rewrite a day").
> - **LINK-65** `CLOCK` (0x63) sets the radio's clock from the PC, as setting it by hand does (GPS-23), and reads it with its source: Console's satellite transfer sets the clock in the same step (SAT-3). Both ports; on Bluetooth after `AUTH` while a PIN lock is on (LINK-30).
> - **LINK-66** The radio record, `what` 14, index 0 (decision 347; radios that say caps2 `RADIO`): Watch (0 1 1), Battery Save (0 7 7 1) and the message sound (0 7 5 5; also in the APRS record), the settings the settings record doesn't hold, read and written as the menu changes them (a value past the menu's answers `invalid`); then, read only, the position the radio would use (GPS-3): its GPS fix (2D or 3D, with the fix's age) or, with none, the fixed position (0 6 9) when it is on. Console reads the radio's place from it instead of the terminal's `gps`.
> - **LINK-23** One request in flight: the PC sends the next only after the answer. The cable's XON/XOFF is off while the link holds the port, since a binary frame can't carry it; a frame and its answer fit the receive and send rings.

> **Spec: cable speed**
>
> - **LINK-10** The cable starts at 115200 8N1 at every boot.
> - **LINK-11** After `HELLO`, `BAUD` proposes a faster rate (target 921600); both switch, and the radio falls back to 115200 unless a `HELLO` arrives at the new rate within 1 s. The radio takes only 115200, 230400, 460800 or 921600, and only a rate its UART reaches within 2 % at the clock it runs: on the 120 MHz clock (PWR-9, APB1 and APB2 at 60 MHz) all four are within 0.2 %. The switch happens after the `BAUD` answer has left at the old rate.
> - **LINK-11.1** Above 115200, a framing error on the cable puts the radio back to 115200 at once (decision 216). A PC that opens the cable at 115200 after a session that didn't put the rate back (a closed tab, a crash, a pulled cable) garbles its first byte at the faster rate; the radio drops back and the PC's next `HELLO` is heard, with no power cycle.
> - **LINK-12** PC10 (UART4 TX) idles high always; cable traffic is queued while the transmitter is keyed.
> - **LINK-13** `AUDIO` is cable only; gaps are dropped, never resent.
>     - **LINK-13.1** Receive audio first (decision 213): while subscribed, the radio streams what the BK4829s put on PA2 (the receivers' audio the decoders hear; the SI4732's broadcast and HF audio reach it too, LINK-13.7) as 12 kHz G.711 µ-law, 8 bits a sample (~12 KB/s; audio to about 5 kHz), in numbered blocks that each decode alone, so a dropped block costs only that block (decision 330; 8 kHz IMA ADPCM until then). The stream carries the slot heard and its squelch; silence (squelch closed) sends nothing but a short keep-alive. Ferrite's own format, not nicFW's.
>     - **LINK-13.2** Transmit audio from the PC (PTT and the PC's mic into the BK4829's mic input over DAC1, the path APRS tones take) is a later step, with every chapter 15 check and PTT held from the PC as remote PTT is today.
>     - **LINK-13.3** Console raises the cable's rate with `BAUD` (LINK-11) when it connects, to 230400 (back to 115200 if the radio doesn't answer), so audio and the screen mirror (LINK-18) fit together. 230400 is the one safe rate for everything over the cable (decision 266); the radio still takes the faster rates for other hosts.
>     - **LINK-13.4** Built (decision 288; 12 kHz µ-law since decision 330, which replaced the 8 kHz ADPCM stream): `AUDIO` (0x56, payload 1 to listen, 0 to stop; the answer the rate, 12000, and a block's samples, 192) and `AUDIO_DATA` (0x57, pushed unasked). The DSP task steps the decoders' 24 kHz down 2:1 to 12 kHz through a 31-tap half-band low-pass (flat to 4.5 kHz, -1.8 dB at 5.5 kHz, -30 dB at 7 kHz, 60 dB down from 8 kHz; 9 multiplies a sample, in fast flash) and codes G.711 µ-law (the 16-bit form, by bit operations; `ferrite_core::rxaudio`, the same code Console decodes with) in blocks of 16 ms: seq (u16), the slot heard, the squelch flag, then 192 bytes of codes, a byte a sample. A block goes while a slot's squelch is open (with that slot), else a keep-alive (the 4-byte head, no codes) each second; about 12.6 KB/s while something is heard (55 % of 230400), 10 B/s while nothing is. Blocks wait in the DSP task's queue (eight, 128 ms) while the cable's send ring is full rather than being dropped (LINK-13.6). There is one format: no older ADPCM mode, and a Console from before decision 330 can't decode the stream. `AUDIO_DATA` is never compressed and stays out of LINK-51's window and count. HELLO's caps say `AUDIO` (16) on the cable only; on Bluetooth `AUDIO` is refused.
>     - **LINK-13.9** *(bench builds only, TERM-38; decision 307)* LINK-13.4's raw mode, for measurements: `AUDIO` 2 (12 kHz) or 3 (16 kHz) streams the decoders' own samples (ADC1's 48 kHz through the 2:1 step, 24 kHz) as 12-bit PCM, with no gain (LINK-13.8 is the listening stream's), in `AUDIO_RAW` (0x58) frames: seq (u16), the first sample's index since listening began (u32), the slot heard, flags (as `AUDIO_DATA`'s, 0x80 a sample held at the 12-bit limits), then 152 samples, two in three bytes (`a | b << 12`, little-endian). Every block goes, whatever the squelch. The answer gives the rate and 152. While it streams, the 48 to 24 kHz step is the data path's (decision 316: flat to 8 kHz), not the decoders' usual 5 kHz low-pass, and the decoders take the same samples. The step from 24 kHz is a 64-tap low-pass at 48 kHz in two 32-tap phases (`ferrite_core::rawaudio`, in fast flash): 12 kHz flat to 4.5 kHz and 67 dB down from 7.5 kHz; 16 kHz flat to 6.5 kHz (-2 dB at 7.5 kHz) and 69 dB down from 10 kHz. 12 kHz is 19.1 KB/s with framing, 83 % of 230400; 16 kHz is 25.5 KB/s and needs 460800, above the 23 KB/s the cable was measured to carry clean (decision 266), so its counts are the judge. A gap in seq is frames lost on the cable; a gap in the first sample's index with seq whole is blocks the radio dropped (its queue of three full). The index counts samples made, not time: the capture pauses while DAC1 plays (AFSK, `txtest`). A user build refuses 2 and 3. `ferrite_link.py PORT audio SECONDS FILE.wav --raw [12000|16000]` sets the cable's rate, writes a 16-bit WAV at the raw rate (silence for missing samples) and reports frames lost, samples missing, clipped blocks and the rate achieved.
>     - **LINK-13.5** Listening is opt-in and never on by itself: it starts only with `AUDIO` 1 from the session, and ends with `AUDIO` 0, a `HELLO`, a new connection, or the session going quiet (ACTIVE_MS); the capture runs for it only meanwhile. Console's Listen (Live View) starts off at every connect and isn't remembered. Its player (decision 331) starts once 250 ms is waiting and keeps at most 750 ms (older audio goes); a short underrun (a lost block, a late one) plays as silence and carries on with the next block as it comes, without waiting for 250 ms again; it waits to refill only after a real stop (nothing for 500 ms: the squelch closed, keep-alives only). With no `AUDIO_DATA` at all for 3 s while on (not even a keep-alive: listening was ended, e.g. by another connection's `HELLO`), Console asks `AUDIO` 1 again; if that is refused or still nothing comes, Listen turns off and says it stopped.
>     - **LINK-13.6** The audio never waits for the screen (decision 290): the DSP task frames each block itself (`rxaudio::frame`) and puts it straight into the cable's send ring, whose bytes the transmit interrupt sends (UART4's TDBE interrupt draining the ring), so a block goes while the UI task draws (redraws of up to 200 ms on a keypress dropped blocks behind the old hand-off: 79 of 2,069 on black, Oct 25, 2026). The thread-mode writers of that ring (the link session, KISS on the cable) hold a flag while they write a frame, and the DSP task puts a frame only while it is clear, so frames never interleave. Audio comes first (decision 331): a thread-mode writer holds the flag only while it copies one whole frame into the ring, never while it works out an answer or draws the Live View (holding it over the whole session pass left the cable idle for most of a redraw: 281 of 2,167 blocks dropped on clear with Live View open, Oct 31, 2026); the DSP task tries its queue again at every 2 ms capture half, not only when a block is made, so the ring is topped up as soon as there's room; it leaves room for one more of the session's frames (`MAX_WIRE`) free, so a session that found room for its answer before working it out still finds it; and while the cable's session listens its events (the Live View) take at most 3 KB/s (`RATE_CABLE_LISTEN`, 4 KB/s otherwise), so the audio's 12.6 KB/s, the events and the answers fit the 23 KB/s 230400 carries. The Live View updates a little slower while Listen is on. Console's player (LINK-13.5) covers a short gap with silence and carries on without waiting to refill. The cable still sends nothing while keyed without Dry TX (TX-43: the Radio task holds the interrupt as it keys) or with a speaker mic (SND-14). The readback's `audio` line counts blocks made, dropped and the times one waited.
>     - **LINK-13.7** The broadcast and HF audio are in the stream (decision 290): the SI4732's audio reaches PA2 ahead of the volume knob (bench, black, Oct 25, 2026: broadcast playing with both BK4829s squelched swung PA2 over its whole range; without, 1,248-1,253), so what is heard is, in order, the first slot with its squelch open (the SI4732 is muted under it, BCR-24), else the broadcast while it plays (the broadcast's slot, flag 2), else HF mode's receiver (no slot, flag 4). Console shows "Broadcast · 101.1 · its station name", or "Hearing HF". The level fits PA2 because the SI4732's own volume is 56 (BCR-7).
>     - **LINK-13.8** The stream has its own level (decision 294): a digital gain between PA2 and the stream's coder, not on the decoders' input, and the sources' own levels (the SI4732's volume, BCR-7; the BK4829's REG_48) never turned live, as both sit ahead of the volume knob. Automatic: before each 2 ms chunk is scaled the gain drops so its peak stays under about -3 dB of full scale (nothing it passes clips); while a squelch is open and peaks stay under about -6 dB it rises by 1/512 a chunk (about 8 dB a second) up to x16 (24 dB); with no squelch open it holds, so a channel's noise between calls never winds it up. Reset when listening starts. A fixed gain, set at a cycle's boundary and held, is the hook for weak-signal modes (not built). The readback's `audio` line gives the gain (Q8: 256 is x1).

> **Spec: remote head**
>
> - **LINK-18** *(shelved, decision 212)* `SCREEN` sends one full frame on subscribe, then the renderer's dirty rectangles, run-length coded.
> - **LINK-19** `KEY` presses the radio's keys from the link as a person would: every front key and the side keys (PF1, PF2) by stock's key code (Appendix G), a short press, a long press, down and up apart, and knob steps (1 to 20 either way). A key held down is let go by `KEY` up, after 30 s, or when the session closes or moves port (LINK-28). On a dark screen a remote key or knob step lights it and acts as well (DISP-15.1, decision 162): the PC or phone can't see that the screen is dark. The radio's own keys keep wake-only.

>   - Never transmit: the PTT codes are not keys here (remote PTT is LINK-20's alone, with its keepalive). While the radio transmits, every remote key is refused (`invalid`: DTMF digits and the tone burst are keys then). Anything a remote key would start that transmits is refused with a toast ("Remote keys: never transmit"): a PTT path, the DTMF dialer's Send, a message sent, Beacon now. The crossband repeater is the one exception: # on its start page starts it, with its own checks and limits (XB-20, decision 161). A setting that makes the radio transmit later by itself (beacons, VOX) changes as `set` over `CMD` changes it (LINK-34), with its own checks (TX-35).
>   - `UI` (and the terminal's `ui`, TERM-37) is text built from the App's own state, the values the drawing code draws, never pixels: the screen (a stable id, its name, the status bar's title); the redraws that changed something and the time since the last; the backlight, the lock, the active slot, a transmission; the status bar (lock, scan, watch, inbox, alert, GPS, Bluetooth, battery %, clock); a toast or popup; the quick menu's rows; home's cards (per slot: letter, header, state, frequency, channel name, mode, tone, shift and power chips, S-meter; the APRS card, which has no chips, its last heard line, beacon line and stations heard instead: `last="Nothing heard yet" beacon="Beacon off" heard=0`); a list's rows (number, label, value, selected, changed from its default, greyed) and its help line; the zones page's own (CHAN-27 to CHAN-30): `head`, the Nearby and zone rows on the page (`kind=nearby` or `kind=zone`, `chips="A SCAN HID"`), the preview (`preview "NAME" "state"`, a `pvrow "name" "place" "frequency"` per channel, `pvfoot`); an editor's value; a question; then the hint bar's pairs, which are also a question's options. Whole lines, `MORE` for the rest. A screen without its own lines yet gives the rest.
> - **LINK-19.4** Ferrite Console's Live View shows every text the radio draws, screen by screen: what the readback carries and Console's look-alike draws together. A check runs it on every screen the simulator reaches (the jump list, home in each slot, layout and holder, broadcast, scan, entry with digits, toasts and alerts, About's pages): the simulator's drawn texts against Console's Live View drawn from that screen's readback (`sim/tests/liveview_corpus.rs`, Console's `tests/e2e/liveview-complete.spec.ts`). Since LINK-19.5 there are none: any gap fails it. Frequency entry reads back its digits, the slot, what is typed (`what=`), the amber note (`note=`), its rows (Band, Step, Transmit; or Channel, Name, Zone, Frequency) and its help, from the screen's own `Entry::info`; a card reads back a scan's hits (`hits=`). Readback-only lines (`state`, `audio`) are never drawn as screen content. Decision 289.
>     - **LINK-19.5** The screen as drawn: `UI` what=3, and a Live View subscribed with `SUBSCRIBE`'s TEXTS flag (2), from a radio whose `HELLO` says caps TEXTS (32), give the readback without the screen's own lines (its rows, values, help) and then `t` lines: the radio draws the screen's content again into a listener that paints nothing and writes each text (`x,y,w,h,font,fg,bg,"text"`: its line box, the font's id, RGB565 in hex, `-` for the screen's own background), each coloured fill of 64 pixels or more (`x,y,w,h,colour`) and each icon or dot (`x,y,w,h,colour,o`) as it comes, in drawing order, one screen row to a line (thin edges join the open line; a line breaks at 225 bytes, worked out item by item so it breaks in the same place whether or not it is being written). Home's default layout keeps its structured cards (meters and card shapes aren't text); its other two layouts and Low Power Mode's home are sent as drawn. Nothing is kept: the listener streams into the line being asked for, and the drawing's record of what is on the panel is put back after, so the screen's own redraws carry on as if nothing ran (checked on every screen of the completeness corpus: the App's bytes unchanged). Every screen fits Live View: at most 48 lines, no line cut. Console places the items as the radio drew them, each text squeezed to the width the radio measured when its font runs wider, icons as round marks. Bluetooth at its unlocked rate (LINK-15.1) raises the Live View's cap to 1 KB/s (`RATE_BT_FAST`), which the screen as drawn needs. Decision 291.
>   - `UI` what=2 (and the terminal's `ui status`) is the compact status: one line, for a slow link (Bluetooth, LINK-36: the whole readback takes seconds there), with the facts a test polls, the same values the whole readback gives: `st scr=Home act=A keyed=- remote=0 mode=xb A=RX/17 B=heard/8 C=-/0 xb=1,1,3`. `scr` the screen's id, `act` the active slot, `keyed`, `remote` and `mode` as the `state` line has them (`keyed` names the slot transmitting, a data key-up such as an APRS beacon or a KISS frame included); per slot its card's state word and meter level (`A=RX/17`: the word as the card's `state=` gives it, `-` for idle and `_` for a space, `RX_muted`); `xb=1,STATE,PASSES` while the crossband repeater runs (as its `xb` line), else `xb=0`. About 70 to 85 bytes, 140 at the very most: always one answer, no `MORE`.
>   - On Bluetooth, past the PIN while a PIN lock is on (LINK-30), as every request.
>   - No screen capture over the link: the drawing code is built for the panel it draws on, so drawing into memory would build all of it a second time (the fast drawing primitives too, in the fast flash), and a frame (150 KB) doesn't fit the 96 KB RAM; a band at a time would need that second build too.
> - **LINK-33** `SLOT` reads a slot's working fields and changes them as the terminal's `slot` does (TERM-35): the same paths, checks, refusals and writes as the keypad; a refusal answers `invalid` with the reason and changes nothing (Appendix G). Decision 137.
> - **LINK-34** (Bench builds only since decision 347: a user build answers "Line commands: not in this build." and leaves caps2 `LINE_CMDS` clear; Console then uses the records.) `CMD` carries one terminal command line (chapter 37's command line: `set`, `get`, `ch`, `slot`, `xb`, `dump`, `help` and the debug commands `bk`, `si`, `mem`, `gpio`, `mic`, `rx`, `gps`, `txtest` ...) and runs it exactly as the terminal does, with its checks and refusals (a refusal answers `invalid` with the terminal's text); its output comes back in whole lines, as many as fit, `MORE` asking for the rest (Appendix G). > - **LINK-35** `HELLO` and `INFO` say which build the radio runs, one byte after the version (`HELLO`) or the callsign (`INFO`): 0 receive only, 1 transmit (`tx`), 2 the retired `tx-dry` build (decision 193; still named for a radio that runs an older image), 3 the `tx` build with Dry TX on (`tx+dry`, TX-48: the PA drive held at 0 until Dry TX is turned off on the radio, read again at every `HELLO` and `INFO`), with bit 7 (0x80) added when the bench commands are in (TERM-38: the bring-up and `tx-bench` builds, so the tx-bench build gives 0x83 from power-on, TX-48.1, and 0x81 once Dry TX is turned off), set from the firmware's cargo features and the Dry TX switch (Appendix G). Decision 144.
>     - **LINK-35.1** `INFO` ends with the unique ID's 12 bytes as the MCU stores them (SELF-8; zeros until read), after the build byte; `ferrite_link.py info` shows it as About does.
>     - **LINK-35.2** `HELLO` ends with a capability byte after the build byte (decision 285): 1 `STREAM` (LINK-50), 2 two `WRITE_MANY` frames in flight (LINK-41.1), 4 this session is compressed (LINK-51, decision 286), 8 `WRITE_MANY` deletes (LINK-41.2), 16 `AUDIO` (LINK-13.4), 32 `TEXTS` (LINK-19.5), 64 channel positions (LINK-53), 128 the quick messages, waypoints, DTMF memories and the event log's events (LINK-54 – LINK-57, decision 327). > - **LINK-36** Bluetooth sends in bursts: at most 20 bytes, then 50 ms with nothing sent, counted from the burst's last byte, so about 280 bytes a second leave for the phone (9600 back to back would be 960). The BT513 sends what has piled up on its UART only once the UART has been quiet for between 30 and 40 ms, and then only the last notification's worth (20 bytes at the module's MTU of 23); the rest is dropped without a sign. On the bench (Oct 14, 2026, Mac): unpaced, a 224-byte UI readback chunk arrived as one 5-byte notification, its tail, while the radio's counters showed all of it sent; 20-byte bursts with 5 to 30 ms gaps lost every readback; 40, 50, 60 and 80 ms delivered 5 of 5. 50 ms keeps a margin over the 40 ms seen to work. A burst left short because nothing more was waiting is topped up only after a full gap, so short answers close together don't add up at the module. The gap is a wait between the Link task's turns, never a busy wait: the cable and the other tasks run on through it. The cable is never paced. Bytes towards the radio need nothing: USART1 receives into a 256-byte ring at the module's 9600, faster than the PC's paced writes (`ferrite_link.py` writes 20 bytes without response every 25 ms, 800 B/s). A bench build's `bt pace B G` (TERM-27) changes the burst and gap until a restart, to find what a phone and module carry.

Bench, Oct 24, 2026 (`research/ble-speed.md`): 160 B / 50 ms lost about 1 reply in 3, a steady trickle of 20-byte pieces lost 7 in 10, 80 B / 50 ms and 160 B / 100 ms passed 10 of 10. `bt pace` sets the fast rate's bursts while USART1 runs fast.

>     - **LINK-20.1** Remote PTT is a `KEY`: `KEY` on keys a slot as its PTT press would (KEY-7): the active slot as PTT A and the side connector, or slot B as PTT B; A or C only while it is the active slot.
>     - **LINK-20.2** It goes through every transmit check a PTT press meets (the build, battery, receive-only channel, AM, the region's band plan or Extend TX, calibration, the relay, busy lockout), on the same path as VOX (VOX-13), and the Radio task's own at the key-up (TX-17); a refusal is answered `invalid` with the reason as text.
>     - **LINK-20.3** A refusal shows on the radio as a PTT's does.
>     - **LINK-20.4** It needs a keepalive every 2 s: no keepalive, no transmit. A lost keepalive unkeys as a cut (TX-47: no end tone, CW ID or 400 ms carrier hold), so the carrier ends 2 s after the last keepalive, not 2.4 s and more.
>     - **LINK-20.5** Only the session that keyed holds it (LINK-28); that session closing or starting over (a new `HELLO` on it, at once), or moving to the other port (LINK-29), unkeys as a cut.
>     - **LINK-20.6** `KEY` off unkeys as a PTT let go.
>     - **LINK-20.7** It unkeys when the transmission ends on the radio (the timeout, TX-30; the Radio task's refusals and the sequencer's stops); the PC's next keepalive is answered `invalid` with why.
>     - **LINK-20.8** The radio's operator wins: a PTT pressed on the radio during a remote transmission ends it and keys nothing until it is let go (then PTT works as usual); a remote `KEY` on is refused while a PTT on the radio is held. Decision 136.
>     - **LINK-20.9** Never on an emergency frequency (TX-35): refused with a toast ("No remote TX: emergency frequency"), and it never opens the second-PTT prompt.
>     - **LINK-20.10** It never answers a second-PTT prompt a person opened.
>     - **LINK-20.11** Nor on the APRS slot or with a message being composed (APRS-18: a PTT there sends or opens one).
>     - **LINK-20.12** The Transmit screen shows it as any transmission, with "Remote" beside the title and "PTT: Stop remote" in the hint bar.
>     - **LINK-20.13** A `txtest` armed (TERM-33) goes out on it as on the next PTT key-up.
>     - **LINK-20.14** On Bluetooth only past the PIN while a PIN lock is on (LINK-30).
>     - **LINK-20.15** On the cable a `tx` build sends nothing while keyed (TX-43): the answers wait in the radio's send queue and leave after the unkey, while the keepalives coming in are still read; so `KEY` is the one request a PC sends without waiting for the last answer (LINK-23), and the radio answers it without waiting for the store or for room for the largest answer (an answer that finds no room is dropped whole).
> - **LINK-37** While the radio transmits, remote keys and knob steps (LINK-19) are refused `invalid` ("transmitting: remote keys wait for the unkey"); remote PTT (`KEY` off, keepalives) is not a key and goes on. What a key would do while keyed is a person's (MENU-30, TX-22.3). Decision 175.
> - **LINK-38** The link keeps answering whatever the screen does: during a scan (the Radio task publishing on every step) and on any busy screen, the UI task yields once a pass and redraws for live changes alone at most every 50 ms (keys and the knob at once), so the Link task answers `HELLO`, `UI` and keys within their timeouts and the cable log keeps flowing. Cable log lines go in whole, never interleaved.

### Settled details

- no pairing, passkey, forgetting or naming on the radio: the MCU never configures the BT513 (stock has no `AT+` strings; its Bluetooth menu is on/off, PB9). The module's own baud and pairing are set from the phone side (FF31 `AT+BAUD`). Ferrite's Bluetooth item is on/off, as stock; access is the radio's PIN while a PIN lock is on (LINK-30), not BLE pairing, which the module handles with the phone. Approved devices (0 9 2 2), Add a device and the on-screen write approval were dropped with their tokens (decision 104).
- the MCU sees a UART, so chunking is the module's and the web app's business: the app writes at most 20 bytes per BLE write unless it negotiates a larger MTU. Nothing in the firmware depends on it.
- After each transmission Ferrite re-asserts PB9 (Bluetooth power) when Bluetooth is on, as stock does after TX (0x08024A14) (decision 76).
- no layout version per record. The record layouts are the radio's own storage formats (Appendix G), so the web app supports firmware versions, read from `HELLO` (LINK-6), as nicFW's RMS is tied to nicFW versions.
